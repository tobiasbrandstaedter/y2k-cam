# ADR-001: Technology stack for y2k

Date: 2026-11-09
Status: proposed, pending spike results from a real iPhone (see Evidence, section "Open measurements")

## Context

y2k is a private PWA for iOS Safari 17 and newer that applies Y2K era camera Looks to photos and videos entirely on the device (QA-6, QA-7). Before anyone writes a feature, the project needs one stack decision that covers: language and build tool, UI approach, how still images are processed (QA-2: Look switch on a 12 MP photo under 0.5 s), how video is decoded, processed per frame, encoded and saved (QA-3, QA-4, QA-5, EX-2, EX-5), where projects and presets live on the device (IM-5, LA-7, QA-8), and how the code is tested.

The riskiest question is offene Frage 1: can a 30 s 1080p clip with a Camcorder Look be exported in at most 60 s on a roughly three year old iPhone (QA-4)? The second is offene Frage 4: are HEIC photos and HEVC/HDR MOV clips from the iPhone camera readable in the browser (IM-3)?

This ADR was written on a Windows machine without access to an iPhone or a Simulator. Every browser capability below was checked against caniuse or WebKit release notes, not memory. Every performance number still has to come from the spikes in `spikes/`, run by the user on their own phone and recorded in `docs/testing/spike-protocol.md`. Decisions marked **pending** say exactly which number confirms or overturns them.

## Decision

A plain TypeScript and Vite project with Preact for the UI, WebGL2 fragment shaders for every Look on both photos and video frames, WebCodecs plus the mediabunny library for video decode, encode and MP4 muxing with audio copied through unchanged, IndexedDB for projects and presets, and Vitest for tests. No framework heavier than Preact, no WebAssembly codec, no server.

Runtime dependencies justified by this ADR: `preact`, `mediabunny` (MPL-2.0, ~11 MB unpacked but tree shakeable), `idb` (ISC, 80 KB, thin IndexedDB promise wrapper). Only `preact` is installed in the skeleton. The video and pwa-ios agents add `mediabunny` and `idb` when they first use them.

### Why these and not the alternatives

**TypeScript and Vite, Preact.** Boring and well documented, which the project principles ask for. Vite serves and builds a PWA with no configuration beyond the browser target. Preact is 4 KB, has the React mental model and documentation, and is enough for a gallery, sliders and an undo stack. Vanilla DOM was considered and rejected: the editor has real UI state (Look, Bausteine, intensity, undo history, export progress), and hand written DOM sync for that is where hobby projects rot. Svelte, Vue and React were rejected as more than needed.

**WebGL2 for all pixel work.** A 12 MP photo is 48 MB of RGBA. Any Canvas 2D `getImageData` loop over it costs hundreds of milliseconds per pass in JavaScript, and a Look is four to eight passes (QA-2 needs all of them in under 500 ms). The GPU does a pass over 12 MP in single digit milliseconds. WebGL2 is in every iOS version since 15. WebGPU is disabled by default on iOS 17 and only ships in iOS 26, so it is not an option for the stated target. Running the same shaders per video frame also satisfies Prinzip 5 and LA-4 with one implementation. Risks: texture memory on 50 MP photos (QA-5) and the GPU context being lost when Safari is under memory pressure; see Consequences.

**WebCodecs plus mediabunny for video.** The alternatives were:

- `MediaRecorder` on `canvas.captureStream()`: real time only (a 30 s clip takes at least 30 s, QA-4 still passes but there is no headroom), bitrate and keyframe control is poor, and keeping the original audio means routing it through Web Audio in real time. Rejected as primary, remains a last resort.
- `ffmpeg.wasm`: 30 MB download, software H.264 encode on an iPhone is far slower than real time, and it needs `SharedArrayBuffer`, which needs COOP/COEP headers that many static hosts cannot set. Rejected.
- WebCodecs with a hand written MP4 demuxer and muxer: possible but mediabunny already does ISOBMFF and QuickTime read and write, exposes `VideoDecoder` and `VideoEncoder` through a small API, has a `Conversion` helper with a per frame `process()` hook, `trim`, progress and cancel (BB-5, EX-4), and copies audio packets when the codec is unchanged. One dependency with an MPL-2.0 licence versus several hundred lines of container code. Accepted.

WebCodecs on iOS 17 has two gaps that shape the design. `VideoDecoder` decodes H.264 everywhere but HEVC only from iOS 17.4, and iPhone camera MOVs are HEVC. There is no `AudioEncoder` or `AudioDecoder` before iOS 26. Therefore: HEVC input on 17.0 to 17.3 goes through the `<video>` element fallback, and audio is never re-encoded in the MVP. Audio Bausteine (BS-15, Release 2) will need either a WebAssembly AAC encoder (`@mediabunny/aac-encoder` exists) or a minimum iOS of 26 for that feature. That is a Release 2 decision.

**IndexedDB for storage.** Since iOS 17 the per origin quota is up to 60 percent of the disk, Home Screen web apps get the same quota as Safari, and WebKit grants `persist()` for Home Screen web apps, which protects against the eviction that would otherwise delete projects after a period without use. IndexedDB holds Blobs, so the original file can be stored as is (QA-8). OPFS is available since iOS 15.2 and would be the right place to stream a large MP4 while encoding instead of holding it in memory; it is not needed until a measurement says the in memory buffer is a problem.

**Vitest.** Same config and transform pipeline as Vite, zero extra setup. Nothing in the Look pipeline runs in Node, so unit tests cover data and math only; everything visual is a device checklist.

## Consequences

Easier:

- One shader implementation per Baustein serves photos and video (Prinzip 5, LA-4). The filters agent writes GLSL and parameter metadata; the video agent only has to feed frames.
- Export, trim, progress, cancel and audio passthrough come from one library call (`Conversion` with `process`). The video agent's work shifts to frame scheduling, memory and the fallback path.
- No build time surprises: Vite with a single browser target, no transpilation for old browsers, no polyfills.
- Storage is boring: one IndexedDB database, two stores (projects, presets), `idb` for ergonomics.

Harder, watch these:

- **HEVC on iOS 17.0 to 17.3** only works through the `<video>` fallback, which is bound to playback speed. For QA-4 that still passes (30 s clip in about 30 to 35 s at 1x) if the device keeps up with 1080p30 texture uploads from a video element. The spike measures dropped frames on this path. If the user base is on 17.4 or newer, the fallback can be dropped.
- **No audio re-encode on iOS 17.** Trimming with passthrough cuts on AAC packet boundaries (about 21 ms granularity), fine. Speed change (BB-7) and audio Bausteine (BS-15) cannot keep audio without an encoder. Document in the Release 2 backlog.
- **HDR input.** iPhone clips are 10 bit HLG (Dolby Vision profile 8.4 in a `hvc1` track). Whether `VideoDecoder` accepts them, and what the colour looks like after `texImage2D`, is only knowable on the device. The input-formats spike reports the colour space and whether a frame decodes. If decode fails, the `<video>` fallback applies; if colours are wrong, the pipeline needs an HLG to SDR tone map pass (the filters agent should plan for a "input transfer" pre pass).
- **Memory.** A 30 s 1080p export at 8 Mbit/s is about 30 MB in a `BufferTarget`, fine. A 3 minute clip (QA-5) is 180 MB plus decoder and encoder queues, and Safari kills pages silently. If the "whole clip over 60 s" run in the video spike reloads the page, switch the output to `StreamTarget` writing into an OPFS file from a worker, then share that file.
- **Texture limits.** `MAX_TEXTURE_SIZE` on A series GPUs is 16384, so 50 MP (8192 x 6144) fits as a texture but three of them (source plus two ping pong buffers) are 600 MB of GPU memory. Rule: preview always at a bounded resolution (long edge 1600 to 2048), export processes full resolution in tiles if the photo exceeds about 20 MP. The image-pipeline spike has a "largest photo" step to see where Safari gives up.
- **WebGL context loss.** iOS drops WebGL contexts under memory pressure. The pipeline must listen for `webglcontextlost`, re-create shaders and textures from the source Blob, and never keep the only copy of anything on the GPU (QA-8).
- **`VideoFrame` as texture source.** Chrome accepts a `VideoFrame` in `texImage2D`; Safari 17 may not. The spike tries it and falls back to drawing the sample into a 2D canvas first, which costs one extra copy per frame. The result table says which path ran.
- **Secure context.** WebCodecs and `navigator.share` need HTTPS. Static hosts provide that; the spike dev server uses a self signed certificate.
- **mediabunny is one person's library.** Active, well documented, MPL-2.0 (file based copyleft: changes to its own files must be published, bundling it unmodified in this app is fine). Pin the version. If it dies, the WebCodecs code stays and only the container layer needs replacing.

### Spike results on the dev machine (not evidence for iOS, only proof that the spikes run)

Chrome 152 on Windows, Intel UHD graphics, synthetic 5 s 1080p30 H.264 clip with AAC tone:

- Mode A (WebCodecs decode, GL effect, H.264 encode, AAC passthrough): 150 frames in 3.34 s, ratio 0.67 of clip length, 0.4 ms per frame in the effect, `VideoFrame` accepted by `texImage2D`, output 5.1 MB MP4 with audio track.
- input-formats: JPEG and MP4 inspection paths run, codec string, colour space, `canDecode()` and first frame decode reported.
- image-pipeline, synthetic 4032 x 3024 JPEG: four pass chain 9 ms at 1600 x 1200 preview, 26 ms at full 12 MP (second tap; first tap 38 and 75 ms with shader warm up), texture upload 35 to 45 ms. Canvas 2D single pass baseline at full resolution 101 ms, so four passes in JavaScript would already be around 400 ms on a desktop CPU before the phone is involved.
- Mode B (`<video>` plus `requestVideoFrameCallback`) produced a valid MP4 but the embedded browser throttled frame callbacks to 1 per second while its pane was in the background. That is an artefact of the test environment, not of the approach. The phone runs the page in the foreground.
